Architecture

One Pod owns each match; the others relay

Two players routed to different replicas still play one game. The pod that completes the match runs the simulation; the other forwards input and relays state over Redis pub/sub.

Chaos testing

Breaking it on purpose

A total database outage caused zero restarts

# postgres scaled to 0 replicas
/ready   → 503
/health  → 200
restarts → 0

PASS readiness reports the dependency failure
PASS liveness stays green, pods not restart-looped
PASS recovered automatically

Liveness deliberately checks nothing external. Had it checked the database, every healthy game server would have been killed at once — turning a dependency outage into a total outage.

A completely broken release shipped zero downtime

# deployed an image that exits on startup
game-server-58bd..  CrashLoopBackOff  restarts=4
game-server-64c6..  Running
game-server-64c6..  Running

deployment  READY=2/2  UP-TO-DATE=1  AVAILABLE=2
traffic     100 requests, 100 × 200

UP-TO-DATE=1, AVAILABLE=2 is a stalled rollout. With maxUnavailable: 0 plus a readiness probe, Kubernetes refused to remove a healthy pod for one that never became ready.

Autoscaling

Scaling on real metrics, not a schedule

  sampled from /cluster during a k6 WebSocket load test

  t+14s   pods=5   players=6    games=3
  t+28s   pods=5   players=20   games=10
  t+42s   pods=6   players=25   games=12
  t+56s   pods=6   players=29   games=15
  t+70s   pods=6   players=36   games=18
  t+84s   pods=8   players=41   games=19   ← maxReplicas reached
  t+98s   pods=8   players=40   games=20

Scale-up and scale-down are deliberately asymmetric: 30 s stabilisation upward, 300 s downward with one pod per minute. Removing a pod drops the WebSocket connections it holds, so wasting capacity is cheaper than disconnecting players.

CPU is an honest proxy here because the 60 Hz loop is CPU-bound — but it’s the wrong long-term signal. A pod holding 200 idle connections looks idle while being near capacity. active_games is the real metric, and it’s already exported.

Infrastructure

  • Multi-stage Docker builds, non-root, 210 MB runtime image
  • Deployments, StatefulSet, Services, Ingress, HPA, ConfigMap/Secret
  • Startup, liveness and readiness probes with distinct responsibilities
  • Prometheus with Kubernetes service discovery; 14-panel Grafana dashboard provisioned from git
  • Helm chart parameterising images, replicas, resources, storage and routing
  • GitHub Actions running integration tests against real Redis and PostgreSQL

Application

  • Server-authoritative 60 Hz simulation with fixed timestep and crossing-based collision
  • Native WebSockets; clients send only paddle direction, and only on change
  • Atomic Redis matchmaking via Lua, avoiding the RPOP/LPUSH race
  • scrypt password hashing with per-user salt and constant-time comparison
  • Pinned-algorithm JWTs; login that can’t be used to enumerate usernames
  • Match history and leaderboard with json_agg to avoid an N+1

Honest limitations

What this is not

  • Single Redis replica — a single point of failure with no failover.
  • The PostgreSQL StatefulSet has no backups, no replication and no point-in-time recovery. Production would use a managed database or an operator.
  • local-path storage pins the volume to one node: it survives the pod, not the node.
  • A terminating pod still drops the connections it holds. The surviving player is now notified, but matches aren’t drained gracefully across a rollout.
  • All load figures come from a single-node local cluster, so they say nothing about multi-node behaviour.

Every one of these is recorded in the repository’s decision log rather than left implied.
